## 一、背景与动机

当前系统是一套基于 ROS2（C++）的 Skye / Gento 双臂遥操驱动，采用主从臂结构：人类操作
FACTR 主臂，动作被映射并下发到从臂（通过 Gento SDK 驱动）。目前该链路是**纯遥操**，
即人类全程持续控制，用于示教数据采集。

现在要在这套系统上叠加一层 **VLA（Vision-Language-Action）策略自主推理执行能力**，
并实现 **Human-in-the-Loop（人在环）DAgger 式数据采集**：

- 策略自主执行任务（rollout）；
- 人类操作员在旁监控，一旦发现策略即将出错或已经出错，通过主臂**接管**控制权，
  用遥操把机械臂纠正回正确轨迹，甚至继续完成任务；
- 这段人类接管期间产生的动作数据，恰好覆盖了"策略当前最薄弱、最需要学习"的状态
  分布，因此比额外采集的完整示教数据效率更高；
- 把这批新数据按类别加权，和历史数据一起聚合，用于训练下一轮策略；
- 循环迭代，随着策略变强，人类接管频率逐渐下降。

这套机制的方法论基础是 DAgger（Dataset Aggregation）及其人在环变体
HG-DAgger / IWR / Sirius，参考文献见文末。

**这不是要新建一套遥操系统**，而是在现有遥操链路的基础上：
1. 新增一个策略推理动作源；
2. 新增一个"控制权仲裁"层，决定当前由谁的动作真正下发到执行器；
3. 新增一套按来源分类打标的数据记录与聚合方案。

## 三、目标与需求

### 功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| F1 | 支持策略自主推理输出接入执行链路 | 新增一个"策略动作"输入源，不改动现有主臂遥操输入源 |
| F2 | 支持人类通过主臂随时接管控制权 | 触发方式：物理按键/开关（优先于置信度自动触发方案） |
| F3 | 接管切换时动作连续、无跳变 | 平滑过渡机制，避免关节角度/速度突变 |
| F4 | 完整记录三类动作流 + 模式切换事件 | 策略原始输出、遥操输出、最终下发指令、模式时间戳 |
| F5 | 按来源对数据自动分类打标 | 自主执行 / 人类接管 / 接管前缓冲 / （未来可选）纯示教 |
| F6 | 接管前反应延迟窗口可裁剪 | 按实测人类反应时间设定缓冲长度，标记为低置信度数据 |
| F7 | 支持离线按类别加权聚合训练集 | 权重方案可配置（起点参考见第六节） |
| F8 | 交还控制权支持两种模式可切换 | （a）纠正到安全区间即交还（b）人工做完整个任务再交还，具体见第七节 |

### 非功能需求

| 编号 | 需求 | 说明 |
|---|---|---|
| N1 | 切换延迟 | 按键触发到执行器实际响应的延迟应控制在可接受范围内（具体阈值见第九节，需与现有遥操链路延迟量级对齐） |
| N2 | 安全性 | 任何时刻只能有一个动作源真正驱动执行器，仲裁逻辑必须有互斥保证，不能出现策略和人类动作同时叠加下发 |
| N3 | 数据完整性 | 记录链路不能因为推理进程崩溃 / 网络抖动而丢失接管窗口附近的数据 |
| N4 | 向后兼容 | 不改动现有纯遥操模式的行为，新增功能必须可通过配置开关关闭，退化为当前系统 |
| N5 | 可观测性 | 需要有实时可视化/日志手段确认当前处于哪种控制模式，便于操作员和调试者判断 |

## 四、系统架构设计

### 整体拓扑

```
┌──────────────────┐        /skye/policy_action
│  VLA 推理进程     │ ─────────────────────────────┐
│ (独立进程/Python) │                               │
└──────────────────┘                               ▼
                                          ┌─────────────────────┐        /skye/follower_cmd
┌──────────────────┐        /skye/teleop_action    │  control_arbiter     │ ───────────────────────► [Gento SDK 驱动]
│  主臂遥操映射节点  │ ─────────────────────────────►│  （新增仲裁节点）     │
│ (现有节点，改造)   │                               └─────────────────────┘
└──────────────────┘                                        ▲
        ▲                                                    │
        │ 接管按键/开关信号                          /skye/control_mode
        └───────────────────────────────────────────────────┘
                                                              │
                                                              ▼
                                                   ┌─────────────────────┐
                                                   │  episode_recorder    │
                                                   │  （新增数据记录节点）  │
                                                   └─────────────────────┘
                                                   订阅：policy_action /
                                                   teleop_action /
                                                   follower_cmd /
                                                   control_mode /
                                                   关节状态 / 相机等观测话题
```

### 新增/改造节点说明

1. **`control_arbiter`（新增，核心节点）**
   - 输入：`/skye/policy_action`、`/skye/teleop_action`、接管触发信号
   - 输出：`/skye/follower_cmd`（真正下发给驱动的指令）、`/skye/control_mode`
   - 内部维护一个状态机（见下）
   - 负责平滑过渡逻辑（见 F3）

2. **`episode_recorder`（新增）**
   - 纯订阅节点，不参与控制链路，避免因记录逻辑阻塞/异常影响实时控制
   - 每个 episode 独立文件（建议 rosbag2 或 HDF5，具体看现有数据管线用什么格式，
     需要与已有数据采集格式对齐，见第九节）
   - 每条记录打 `source` 标签

3. **主臂遥操映射节点（现有节点，需要小改）**
   - 现状：大概率是直接把映射后的动作发布/下发到执行器话题
   - 改造点：把"直接下发"改为"发布到 `/skye/teleop_action`，交给 arbiter 决定是否
     真正执行"，即在现有节点和执行器之间插入一层间接

4. **VLA 推理进程（新增，独立于本仓库）**
   - 不一定用 C++ 实现，大概率是独立 Python 进程（模型推理框架决定）
   - 通过 ROS2 Python 客户端或 rosbridge 发布 `/skye/policy_action`
   - 需要接收观测话题（相机、关节状态等）作为输入

### 控制模式状态机

```
        接管信号触发
AUTONOMOUS ──────────────► TRANSITION_TO_HUMAN ──(混合过渡完成)──► HUMAN
    ▲                                                                │
    │                                                                │
    └──(交还信号触发)── TRANSITION_TO_AUTO ◄────────────────────────┘
```

- `AUTONOMOUS`：仲裁节点透传 `/skye/policy_action` → `/skye/follower_cmd`
- `TRANSITION_TO_HUMAN`：短时间窗口内，对策略当前目标位姿与人类主臂目标位姿做
  插值混合（线性混合或阻抗控制柔顺过渡，与现有 `run_marvin_m6_impedance.sh`
  的阻抗控制方案对接，具体插值方式需要结合小臂控制器能力确定）
- `HUMAN`：仲裁节点透传 `/skye/teleop_action` → `/skye/follower_cmd`
- `TRANSITION_TO_AUTO`：交还发生时同理做平滑过渡（是否需要这个过渡态，取决于
  第七节里选择的交还策略）

### 话题/消息定义建议

| 话题名 | 消息类型（建议） | 说明 |
|---|---|---|
| `/skye/policy_action` | 自定义 msg，字段建议：`header`（含时间戳）、关节/末端目标（需与现有 `follower_cmd` 保持同一表示，绝对位姿 or 增量、坐标系需一致）、`policy_version`（字符串，标识模型版本） | 策略推理输出 |
| `/skye/teleop_action` | 同上结构，去掉 `policy_version` | 主臂映射输出 |
| `/skye/follower_cmd` | 沿用现有类型，不改动 | 最终下发指令，现有驱动节点消费此话题 |
| `/skye/control_mode` | 自定义 msg 或 `std_msgs/String`，枚举：`AUTONOMOUS / TRANSITION_TO_HUMAN / HUMAN / TRANSITION_TO_AUTO` + 时间戳 | 模式状态 + 切换事件 |
| `/skye/intervention_trigger` | `std_msgs/Bool` 或按键硬件对应的自定义 msg | 接管/交还的原始触发信号 |

> 具体消息类型定义（.msg 文件）需要参考仓库现有 `docs/ros_interfaces.md` 里已有的
> 命名规范和字段习惯来对齐，避免和现有接口风格不一致。

## 五、数据记录与标注方案

### 记录内容（每个时间步）

- 时间戳（统一用 ROS 时钟，避免多进程时钟不同步）
- `policy_action`（如果该时刻策略在推理，无论是否被执行都记录）
- `teleop_action`（如果该时刻人类在操作）
- `follower_cmd`（实际下发的，即训练用的"标签"）
- `control_mode`
- 观测数据（相机图像、关节状态等，与现有示教数据采集格式保持一致）

### 数据分类（离线处理阶段打标，参考 Sirius 四类划分）

1. **自主执行数据**：`control_mode == AUTONOMOUS` 的时间步
2. **人类接管数据**：`control_mode == HUMAN` 的时间步
3. **接管前缓冲数据**：`AUTONOMOUS → TRANSITION_TO_HUMAN` 触发时刻往前推 N 帧
   （N 根据实测人类反应延迟标定，建议先取一个保守值如 300–500ms 对应的帧数，
   后续通过实验调整），这部分数据**不计入"合格自主执行数据"**，单独存档，
   默认不参与训练或参与时降权
4. **（可选）示教数据**：如果系统同时保留纯示教采集模式，单独归类

## 六、训练侧数据聚合与加权方案

参考 IWR / Sirius 的加权思路，不要用"新旧数据 1:1 直接拼接"，而是分类独立加权：

- 起点参考：Sirius 消融实验显示，接管数据在训练 batch 中的目标占比在 50% 附近
  时性能最优，两侧偏离都会下降——这只是别人任务上的经验值，**必须在自己任务上
  重新做类似的消融**，不能直接套用。
- 建议至少拆分三类权重（示教 / 自主执行 / 人类接管），每类权重独立可调，
  而不是单一的"新旧数据比例"这一个参数。
- 接管前缓冲数据默认排除在训练集外，作为后续分析（比如做失败检测器）的素材。

## 七、交还控制权策略（需要人工决策，见第九节）

有两种策略，各有取舍，需要在开发前明确选择哪一种（或做成可配置）：

- **策略 A：纠正到安全区间即交还**——数据更聚焦在失败点附近，单次接管耗时短，
  采集效率高，但学到的更多是"如何避免/走出具体错误"，不是长程恢复能力。
- **策略 B：人工做完整个任务再交还**——数据里包含完整的"如何从困境一路救回来"
  的语义，对训练策略的长程恢复能力更有帮助，但操作员负担更重、单次接管耗时长。

建议：v1 先实现策略 A（工程更简单，仲裁节点逻辑更清晰），策略 B 作为后续迭代项。

## 九、需要人工补充确认的信息（请填写后再转发给开发 AI）

以下信息我无法从公开 README 获取，直接影响接口设计是否能对齐现有系统，**务必确认**：

1. **`docs/ros_interfaces.md` 的完整内容**：现有话题列表、消息类型定义、命名规范
   （直接把文件内容贴给 AI，比让它猜测更可靠）
2. **`docs/dev_plan.md` 的完整内容**：确认 P5（夹爪）是否已经完成，会不会和本方案
   的 P6 产生依赖冲突
3. **现有主臂遥操映射节点的具体名称和当前发布话题**：本文档假设它"直接下发到执行
   器话题"，需要确认真实实现方式
4. **动作表示方式**：绝对位姿还是增量位姿？关节空间还是笛卡尔空间？频率是多少
   Hz？这直接决定 `/skye/policy_action` 和 `/skye/teleop_action` 的消息字段设计
5. **现有示教数据采集用的存储格式**：rosbag2？HDF5？自定义格式？`episode_recorder`
   需要与之兼容，否则会产生两套互不兼容的数据格式
6. **VLA 推理进程的技术栈**：用什么框架（如 LeRobot / OpenVLA 类框架）、是否已有
   现成的 ROS2 接口、推理频率大致多少
7. **接管触发硬件方案**：主臂上是否已有可用的物理按键/开关？还是需要新增硬件？
   触发信号目前怎么接入到 ROS2（GPIO/串口协议）
8. **人类反应延迟的实测值**：如果没有实测过，建议先做一轮简单测试（比如让操作员
   在随机时刻按键，测反应时间分布），用于标定第五节里的缓冲窗口长度 N
9. **切换延迟的可接受阈值（N1 对应）**：现有遥操链路本身的延迟量级是多少，新增
   仲裁层引入的额外延迟预算是多少
10. **策略 A / 策略 B（第七节）的选择**：先做哪一种，或者要不要一开始就做成可配置
